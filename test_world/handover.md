## 1. 這個模組在做什麼

模擬一台裝著**全方位相機**的小車,在一個矩形場地裡看到的景象。場地四面牆的上緣有一條固定的高低起伏「稜線」(可作為視覺定位的地標),地板上立著數根圓筒障礙物。相機輸出 **64×48 的全景灰階影像**:亮背景(天空)、灰地板、所有物體以同一種黑色剪影呈現,並疊加光照慢漂移、旋轉動態模糊、感測雜訊與 8-bit 量化——刻意模擬廉價感測器的觀測品質,典型用途是 RL 視覺導航的觀測來源。

**本模組只負責「世界長什麼樣 + 從某個位姿看出去是什麼景象」。** 車子怎麼移動(物理)、能不能穿過東西(碰撞)、看到影像後做什麼(策略)都不在這裡,詳見第 6 節的系統迴圈。

## 3. 架構:World 與 PanoCamera 的責任切分

### 切分原則

整個設計只有一條核心原則:**「隨時間演化的狀態」與「觀測」分離**。

- `World` 持有幾何與狀態。狀態(目前只有光照增益)**只由 `step(dt)` 推進**,和有沒有人拍照、拍了幾張完全無關。
- `PanoCamera` 持有感測器參數,`render()` 是**純函數**:讀世界、算影像,不改動世界也不改動自己。

這條線劃下去之後自然得到三個性質(`test_world.py` 以回歸測試逐一守住):同一瞬間重複拍照結果完全相同且無副作用;同一世界可同時掛多台參數不同的相機(訓練用感測器相機 vs 高解析無雜訊除錯相機,見 `fig4_two_cameras.png`);光照統計只依賴模擬時間,跳幀、重播、離線重渲染都不會扭曲它。

### World(幾何 + 狀態)

```
World(lights_on=True)
├── 建構時固定的幾何
│     perim, sky_s, sky_h     牆面稜線(SKYLINE_SEED 決定,每次建構相同)
│     cyl                     圓筒陣列 (N,4):cx, cy, r, h
├── 隨時間演化的狀態
│     _gain                   光照增益(OU 過程)
│     step(dt, rng)           推進世界 dt 秒 ← 唯一改動狀態的入口
│     reset()                 增益歸 1(episode 之間)
│     gain                    唯讀 property
├── 純查詢(不改任何狀態)
│     wall_hit(x, y, alpha)   → (距離, 周長參數 s),向量化射線投射
│     skyline_at(s)           → 該周長位置的牆頂高度
│     clearance(x, y)         → 點到最近障礙物表面的距離(給物理用)
└── 舊介面相容包裝
      render(x, y, θ, ω, rng) = step(1/VISION_FPS) + 預設相機拍照(見第 7 節)
```

### PanoCamera(感測器)

```
PanoCamera(width, height, cam_h, el_top, el_bot,
           blur_exposure, pix_noise, quantize, levels)
└── render(world, x, y, theta, omega=0.0, rng=None)
      → (img[H×W] float 0..1, valid_light)
```

所有參數預設取自 `config`,可逐台覆寫——這就是換一顆除錯鏡頭或做域隨機化的方式,不需要碰 config 或 world。`levels = (背景, 地板, 剪影, 關燈亮度)`,預設 `(0.80, 0.48, 0.10, 0.02)`。

⚠️ **注意**:參數在 `__init__` 時**複製**,建構後改 `config` 不會影響已存在的相機。要不同參數就建新相機——這是刻意設計(相機是值物件),但和舊版「每次 render 讀 config」的行為不同,遷移時留意。

## 4. 座標與資料約定(下游整合必讀)

**世界座標**:場地為 `[0, ARENA_W] × [0, ARENA_H]`,單位公尺。角度為標準數學約定:x 軸正向為 0,逆時針為正,弧度制。

**全景欄位(重要,易踩雷)**:影像第 k 欄對應車體方位角 β = k·(2π/W)。**col 0 = 車頭正前方,欄位隨逆時針方位遞增**——也就是往車子的**左邊**遞增。顯示或解碼端必須採同一約定,否則全景會左右鏡像,而且因為場景大致對稱,鏡像錯誤**不容易用肉眼發現**。`test_world.py` 的「欄位約定」檢查(正對圓筒時暗段貼齊 col 0)就是為此而設。

**仰角行**:行 0 = `EL_TOP`(最高仰角),最末行 = `EL_BOT`,線性內插。仰角 < 0 的行屬於地板。

**周長參數 s**:沿牆繞場一圈的一維座標,順序為下牆(y=0,x 遞增)→ 右牆(x=W,y 遞增)→ 上牆(y=H,x 遞減)→ 左牆(x=0,y 遞減),總長 `perim = 2(W+H)`。稜線紙帶就貼在這條軸上,`wall_hit` 回傳的 s 直接餵給 `skyline_at`。

**影像數值**:float64,值域 [0,1],預設經 8-bit 量化(所有值為 k/255)。`valid_light` 目前 = `lights_on`;若你的下游需要別的語意(例如「增益在合理範圍內」),改 `PanoCamera.render` 的回傳即可,測試只檢查回傳為 2-tuple。

## 6. 系統迴圈:怎麼把它接進模擬

```python
world = World()
cam   = PanoCamera()
rng   = np.random.default_rng(episode_seed)

world.reset()
for tick in range(n_ticks):
    # 1) 物理:移動車子(不在本模組內)
    x, y, th, om = physics_step(action, ...)
    #    碰撞偵測用 world.clearance(x, y) < ROBOT_RADIUS,
    #    頻率跟物理步,不跟視覺幀率——兩張照片之間也可能撞牆。

    # 2) 世界:推進狀態(光照)
    world.step(dt_tick, rng)

    # 3) 視覺:到了視覺幀才拍(想跳幀就跳,不影響世界)
    if tick % ticks_per_frame == 0:
        img, ok = cam.render(world, x, y, th, om, rng)
        action = policy(img)
```

三個常見誤解,交接時務必傳達:

1. **`wall_hit` 不是碰撞偵測。** 它量的是「沿視線方向多遠看到牆」,是眼睛的一部分;車身可能側面貼牆 5 cm 而所有視線都量到 3 m。碰撞請用 `clearance()`,而且要在每個物理步檢查。
2. **本模組不會擋車也不會警告。** 車子若被外部物理放到場外,`wall_hit` 只保證不回傳負距離,不保證畫面有意義。
3. **光照演化由 `step(dt)` 負責,不是 `render`。** 忘了呼叫 `step`,燈就永遠不動(增益停在 1.0)。

## 7. 舊介面已移除

正式版 `World` **不含任何成像邏輯**——舊式 `World().render(x, y, θ, ω, rng)` 單類介面已刪除。所有成像一律經 `PanoCamera.render(world, ...)`,狀態演化一律經 `world.step(dt, rng)`。若接手時發現外部程式仍呼叫 `world.render(...)`,直接改寫成:

```python
world.step(1.0 / C.VISION_FPS, rng)          # 舊 render 隱含的一幀光照推進
img, ok = cam.render(world, x, y, th, om, rng)
```

⚠️ 相機參數在**建構時複製** config 值;執行期改 config 不影響既有相機,要不同參數就建新相機(例如測試用 `PanoCamera(pix_noise=0)`,不要 monkeypatch config)。

## 8. 成像管線細節(PanoCamera.render 內部)

依序:(1) 產生 W 個方位角,col 0 = 車頭;(2) 牆剪影——`wall_hit` 得距離與 s,`skyline_at` 得牆高,`arctan2` 換算頂 / 底仰角,近牆高遠牆矮;(3) 圓筒剪影——角半寬 `γ = arcsin(r/dc)`(切線幾何),高度用最近點距離 `dc − r`;車在圓筒內部則跳過該筒;(4) 上色——背景 / 地板 / 剪影三種亮度,**剪影取聯集即可**,因為所有物體同一種黑,不需深度排序;(5) 乘上 `world.gain`(關燈則整張設為關燈亮度);(6) 旋轉模糊——拖影像素數 = `|ω|·曝光 / 每欄角寬`,整數像素盒狀平均,**方向與 ω 同號**(推導:曝光期間特徵掃過欄位 [β, β+ωT],故 ω>0 往高欄位拖);(7) 加雜訊、裁 [0,1]、8-bit 量化。

## 10. 測試與診斷

```bash
python3 test_world.py [輸出資料夾]     # 24 項檢查 + fig1–fig4;任何 FAIL → exit 1
```

檢查方法論:**獨立實作對照,不重用被測程式的公式**。牆距離用逐步射線行進重算(max err ≈ 1e-4 m);周長參數 s 反推回牆面座標比對命中點(~1e-15 m);圓筒角寬比對切線公式 `2·asin(r/dc)`;`clearance` 比對所有障礙物邊界的密集點雲;OU 統計直接長時間 `step` 量穩態 std(±10%)**與 lag = τ 的自相關 ≈ e⁻¹**(後者驗證時間常數以秒計而非以幀計)。解耦性質也在測試範圍:render 純函數(拍照不改 gain)、光照與拍照解耦(拍 300 張 vs 0 張軌跡相同)、多相機參數覆寫生效。

診斷圖:`fig1` 俯視圖 + 稜線輪廓;`fig2` 多位姿全景(含關燈);`fig3` ±ω 模糊比較(含差影)+ 增益漂移 vs 目標 ±σ 帶;`fig4` 感測器相機 vs 除錯相機同瞬間對照。

**量測技巧備忘**:同一仰角行常同時看到多根圓筒,量特定目標的角寬必須取「包含目標欄位的連續暗段」(含環繞),不能整行閾值計數。之後若做障礙物偵測,同理。

## 11. 已知簡化(刻意的,不是 bug)

**圓筒平頂近似**:所有覆蓋欄位都用最近點距離 `dc − r`,但角邊緣真實距離漸增至 `√(dc² − r²)`,真剪影頂緣應微微下彎。64 欄解析度下影響極小;若未來提高解析度或要做精確幾何監督訊號,這裡要改成逐欄距離。

**車在圓筒內 → 該筒消失**:成像端不處理穿透,交由物理保證不發生。若物理不能保證,合理替代是讓畫面變暗。

**模糊整數截斷**:`int(blur_px)` 使次像素轉速完全無模糊、跨過一像素時不連續;快轉時 O(n) 次 roll 可換 cumsum 盒狀濾波。目前對 RL 觀測影響可忽略。

**`valid_light` 語意**:目前只是 `lights_on` 的別名,是佔位定義,下游若有更精確需求(增益範圍檢查等)請重新定義並更新測試。

## 12. 給接手者的地雷清單(按踩到的痛程度排序)

1. **欄位鏡像**:col 隨逆時針遞增(往左)。接顯示器、接策略網路、接任何座標轉換前,先跑一次 `test_world.py` 的欄位約定檢查確認兩端一致。鏡像錯誤在對稱場景裡肉眼看不出來,但定位會整個學歪。
2. **忘記呼叫 `world.step(dt)`**:光照凍結在 1.0,訓練出來的策略對光照漂移零韌性,而且不會有任何錯誤訊息。把 `step` 放進模擬主迴圈,不要放在視覺分支裡。
3. **相機參數是建構時複製的**:執行期改 config 不影響既有相機。要 sweep 參數就建新相機;寫測試不必再 monkeypatch config,直接 `PanoCamera(pix_noise=0)`。
4. **碰撞頻率**:`clearance` 檢查要跟物理步。只在視覺幀檢查的話,高速下車子會在兩幀之間穿進圓筒,然後該圓筒從畫面上消失(見第 11 節),除錯時非常困惑。
5. **改 `SKYLINE_SEED` = 換世界**:稜線是定位地標,種子一改,所有依賴地標的已訓練模型作廢。把種子當成場地版本號管理。
6. **改動 `world.py` 前先跑 `test_world.py`,改完再跑**:24 項檢查涵蓋幾何、光照統計、模糊方向、欄位約定與解耦性質;歷史上的五個 bug 各有守門測試,退化會被抓到。

## 附錄 A:光照增益 gain 的原理

**它是什麼**:全域亮度倍率,模擬環境光的緩慢波動(電壓、日光燈、雲影)。成像時整張影像乘上它,亮暗等比例縮放——這是「環境光」的模型,不是感測器偏置(偏置會是加法)。

**數學形式**:OU(Ornstein–Uhlenbeck)過程——彈簧上的珠子被隨機踢:

```
dg = −(g−1)/τ · dt + σ·√(2/τ) · dW
```

彈簧項把 g 拉回 1,力道由 τ(`LIGHT_TAU`)決定:偏差每過 τ 秒衰減到 e⁻¹,兩時刻亮度相關性 = e^(−Δt/τ)。雜訊係數 σ√(2/τ) 是特地湊的:代入 OU 穩態變異數公式 s²τ/2 得到恰好 σ²——**穩態 std 恰等於 `LIGHT_GAIN_STD`,且與 τ 無關**,兩顆旋鈕互相獨立:σ 管「漂多大」、τ 管「漂多慢」。

**離散化**(`world.step(dt, rng)` 內):

```python
g += -(g - 1) * dt / τ + σ * sqrt(2 * dt / τ) * ξ    # ξ ~ N(0,1)
```

雜訊乘 **√dt** 是布朗運動的基本標度:獨立隨機踢的變異數相加,要讓「走完 1 秒的總效果」不依賴切多細,每步變異數必須 ∝ dt。原版 bug 正是這裡:彈簧項沒乘 dt(按幀計)、雜訊按秒計,兩種時間單位混用。後果可精算:退化成 AR(1),穩態 std = σ·√((2/FPS)/(2−1/τ)) = 0.00962,與實測 0.0096 吻合到第四位;記憶長度也變成 τ **幀**(0.17 秒)而非 τ **秒**。修正後理論值 0.0501、實測 0.0481。

**架構位置**:g 是**世界的狀態,不是相機的**——燈亮不亮跟有沒有人在拍照無關。所以它只被 `world.step(dt, rng)` 推進,`PanoCamera.render` 只讀 `world.gain` 來乘,不碰它。成像順序:上色 → **乘 gain** → 模糊 → 加雜訊 → 量化——gain 在感測雜訊之前,因為它是場景亮度的一部分,雜訊是感測器的事。`reset()` 在 episode 之間把 g 歸 1。

**為什麼 RL 需要它**:亮度恆定時,策略會偷懶記絕對灰階值(「牆頂就是 0.8 對 0.1 的那條交界」);加了慢漂移,絕對亮度變成不可靠訊號,網路被迫學**對比和幾何**——才是搬得上真實感測器的特徵。「慢」也是刻意的:真實光照本來就時間相關,白雜訊式閃爍反而會教網路學逐幀平均這種真實世界用不上的技巧。

**邊角**:g 未裁切;σ 維持 0.05 等級時 5σ 事件才會讓背景飽和,可忽略;若把 σ 調到 0.2 級,應對 g 本身加裁切以免出現負亮度。

## 附錄 B:wall_hit 的原理

**它回答的問題**:「從 (x, y) 沿方位 α 看出去,多遠處、牆邊哪一格看到牆?」——量的是**視線長度**,不是車身淨空(那是 `clearance` 的事)。

**基本數學**:光線 `(x,y) + t·(cos α, sin α)` 對四條牆直線各解一次交點(一行除法),得四個候選 t,然後用三道濾網剔除不合法者:

1. **方向濾網**:光朝右飛才解右牆(`cx > eps`),依此類推。副作用:場內任一條光頂多剩兩個候選(水平、垂直各一面),後面實為二選一。
2. **負 t 濾網**(修正 #4):`t = where(t ≥ 0, t, inf)`,光不能撞到出發點背後。場內永不觸發,專防場外的「身後鬼牆」。
3. **牆段濾網**:直線無限長、牆不是——交點必須落在實際牆段內(帶 1e-6 容忍度,防牆角浮點誤殺)。

淘汰者設 inf,`argmin` 取最近合法命中。凸矩形內每條光恰好從一面牆離開,不需排序;打在正牆角時兩牆 t 相等,argmin 取先者,無妨——因為兩牆在角上的 s 相同(見下)。

**周長參數 s 的設計**:把二維命中點壓成「沿牆逆時針走的里程」:下牆 `s = hx`、右牆 `s = W + hy`、上牆 `s = W+H+(W−hx)`(反向,因逆時針走上牆時 x 遞減)、左牆 `s = 2W+H+(H−hy)`。關鍵性質是**牆角連續**(角落兩側算出同一個 s),這正是「稜線是一條環形紙帶」能成立的原因:`render` 不需要知道在看哪面牆,只拿 s 查 `skyline_at`,全景裡的稜線跨牆角不會跳。回傳 s 而非座標,因為唯一下游就是這條紙帶。

**向量化與數值防護**:64 條光整批算——四面牆各產生 (K,) 候選,疊成 (4,K),沿牆軸 argmin,fancy indexing 抽贏家;分支全用 `np.where`。`eps = 1e-9` 擋幾乎平行於牆的方向(該方向由另一對牆接住);`errstate` 壓除零警告(where 兩分支都會先求值);`tf = where(isfinite, t, 0)` 防 `inf × cos` 的 NaN 汙染(該項反正已被排除)。

**設計筆記——牆用射線、圓筒不用**:圓筒剪影有閉式解(角半寬 `arcsin(r/dc)`、距離 `dc − r`),不需射線;牆需要射線是因為稜線高度逐點不同,必須知道視線打在哪一格才能查紙帶。本渲染器是混合式:解析幾何能一步到位的用解析,需逐方向查表的才投射線。未來加「表面有花紋的方形障礙物」走射線,加「素色圓柱」走解析。

**邊界行為與驗證**:場外的點某些方向四候選全 inf → 距離 inf → 剪影退化成線,畫面怪但不崩潰(符合職責:不擋車、不警告、只保證不說謊)。驗證用兩個獨立方法:距離以逐步射線行進重算 300 條隨機光線(max err ≈ 1e-4 m,即行進步長量級);s 反推回牆面座標比對命中點(誤差 ~1e-15 m,純浮點雜訊)。
